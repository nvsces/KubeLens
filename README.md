# KubeLens

Kubernetes в строке меню macOS: переключение контекста и namespace в два клика, редактор
kubeconfig (кластеры, пользователи, импорт/экспорт, несколько файлов) и окно ресурсов кластера —
поды, деплойменты, сервисы, ингрессы, конфиги, секреты, ноды: таблицы, YAML, describe, события,
логи, exec, port-forward, scale, rollout restart, удаление, создание из YAML.

## Установка

Скачайте `KubeLens-1.0.dmg` со [страницы релизов](https://github.com/nvsces/KubeLens/releases)
и перетащите в «Программы». Требуется macOS 14.4+ (Apple Silicon и Intel — универсальный бинарник).
Для окна ресурсов кластера нужен `kubectl` в PATH (или путь в настройках).

Приложение без окна в Dock (`LSUIElement`) — иконка-штурвал в строке меню с именем текущего контекста.
Главное окно открывается из меню («Открыть KubeLens…», ⌘O) и при первом запуске.
Автозапуск: Настройки → «Запускать при входе в систему».

## Сборка из исходников

```bash
./make_app.sh && open KubeLens.app          # локальная сборка, ad-hoc подпись
./make_dmg.sh 1.0                            # DMG с Developer ID и нотаризацией
./make_dmg.sh 1.0 --no-notarize              # только подпись
python3 gen_project.py                       # пересобрать .xcodeproj после добавления файлов
```

Сборка идёт через `xcodebuild` (`KubeLens.xcodeproj`), а не `swift build`: SPM-бинарник тянет
rpath на локальный Xcode-тулчейн и на машине без Xcode не запускается. `Package.swift` оставлен
для работы с исходниками в редакторе. Внешних зависимостей нет: YAML разбирает собственный парсер
(`YAML.swift`) под подмножество, которым пишут kubeconfig; порядок ключей и неизвестные поля
(`extensions`, `as-groups`, …) сохраняются при записи.

## Что умеет

**Строка меню** — список контекстов из всех файлов `$KUBECONFIG` (или `~/.kube/config`),
клик переключает; подменю Namespace с отметкой текущего; имя контекста рядом с иконкой.

Тема окон переключается в настройках («Оформление» → Как в системе / Светлая / Тёмная)
или из строки меню, пункт «Тема». По умолчанию приложение следует теме macOS.

**Окно** — три колонки: файлы → контексты (с поиском по имени, кластеру, пользователю,
namespace) → детали. В деталях:

- **Контекст** — кластер, пользователь, namespace (список из кластера через kubectl);
  готовые команды `kubectl config use-context …` и `kubectl --context=… -n …` для копирования.
- **Кластер** — адрес, CA (встроенный base64/PEM, файл или нет), `insecure-skip-tls-verify`,
  `proxy-url`, `tls-server-name`; переименование с обновлением ссылок из контекстов.
- **Пользователь** — токен, файл с токеном, клиентский сертификат, логин/пароль, exec
  (команда, аргументы, env, `interactiveMode`, `provideClusterInfo`), auth-provider, impersonate.
  Секреты скрыты, показываются переключателем.
- **YAML** — этот контекст (`--minify`) или весь файл, с маскировкой секретов
  (`DATA+OMITTED` / `REDACTED`, как у `kubectl config view`) или без (`--raw`).

Операции над контекстами (правый клик): использовать, переименовать, дублировать, удалить
(с предложением убрать осиротевшие кластер и пользователя), экспортировать в отдельный файл
(`--flatten`: файлы сертификатов встраиваются), скопировать в другой файл.

**Файлы** — в сайдбаре все файлы цепочки `$KUBECONFIG` (помечены «kubectl») плюс добавленные
вручную; можно создать пустой kubeconfig. Импорт другого файла (кнопка или drag&drop в окно) —
слияние с выбором поведения при совпадении имён: добавить с суффиксом `-2` (ссылки контекстов
на переименованные кластеры/пользователей обновляются), оставить существующие, заменить.

**Проверить связь** — `kubectl version` через контекст: версия сервера и время ответа, либо
текст ошибки (TLS, auth, недоступность).

## Ресурсы кластера

Кнопка «Ресурсы кластера» в карточке контекста (⌘K) или пункт в строке меню открывает окно
кластера — по одному на контекст, можно держать несколько.

- **Сайдбар** — виды ресурсов по разделам: Нагрузки (Pods, Deployments, StatefulSets, DaemonSets,
  ReplicaSets, Jobs, CronJobs, HPA), Сеть (Services, Ingresses, Endpoints, NetworkPolicies),
  Конфигурация (ConfigMaps, Secrets, ServiceAccounts, ResourceQuotas, LimitRanges),
  Хранилище (PVC, PV, StorageClasses), Доступ (Roles, RoleBindings, ClusterRoles, ClusterRoleBindings),
  Кластер (Nodes, Namespaces, Events, CRDs). Внизу — активные port-forward и кнопка Terminal
  с уже выставленным контекстом.
- **Таблица** — колонки как у `kubectl get` (статус подов с причиной CrashLoopBackOff/ImagePullBackOff,
  Ready, рестарты, узел; для сервисов порты и external IP; для нод роли и версия и т. д.),
  выбор namespace или все сразу, фильтр по любой колонке, автообновление (интервал в настройках),
  контекстное меню с действиями, ⌫ — удалить.
- **Карточка объекта**:
  - *Обзор* — по виду: контейнеры пода с состоянием, образами, портами, ресурсами и причиной
    падения; реплики и стратегия деплоймента; порты сервиса; правила ингресса (с открытием
    в браузере); данные ConfigMap; данные Secret с расшифровкой по переключателю; ресурсы и
    taints ноды; labels, annotations, conditions, владелец.
  - *YAML* — редактируемый манифест (без status и managedFields, можно включить), ⌘S применяет
    через `kubectl apply`.
  - *Describe* — вывод `kubectl describe`.
  - *События* — события объекта.
  - *Логи* (поды) — потоковые `kubectl logs -f`: выбор контейнера, предыдущий запуск, метки времени,
    хвост 100/500/2000/все, фильтр, перенос строк, подсветка error/warn.
- **Действия** — удалить (обычно или `--force`), масштабировать, rollout restart, shell в контейнере
  (открывается в Terminal.app), port-forward к поду или сервису, cordon/uncordon/drain ноды,
  запустить CronJob сейчас, приостановить/возобновить, скопировать `kubectl get …`.
- **Создать** (+) — YAML-редактор с шаблонами Deployment/Service/Ingress/ConfigMap/Secret/Namespace/CronJob;
  namespace из тулбара подставляется, если в манифесте не указан.

Весь обмен с кластером идёт через `kubectl` (`get -o json`, `apply -f -`, `logs -f`, `port-forward`…):
так работают любые способы аутентификации из kubeconfig — exec-плагины облаков, OIDC, сертификаты.

## Как это устроено

- Переключение контекста пишет `current-context` в **первый файл `$KUBECONFIG`** — так же его
  читает kubectl. Если контекст живёт в файле вне цепочки, `current-context` пишется туда,
  а приложение подсказывает `export KUBECONFIG=…`.
- Namespace пишется в тот файл, где определён контекст (как `kubectl config set-context --current`).
- Перед каждой записью — копия файла в `~/Library/Application Support/KubeLens/backups/`
  (по умолчанию 20 на файл). Запись атомарная, права `0600`.
- Правки снаружи (kubectl, редактор, `aws eks update-kubeconfig`) подхватываются сразу.
- `KUBECONFIG` и `PATH` читаются из логин-шелла (`$SHELL -ilc`), потому что GUI-приложения
  их не наследуют. Без kubectl работает всё, что касается файлов kubeconfig; окно ресурсов,
  список namespaces и проверка связи требуют kubectl.
- YAML объектов кластера показывается своим эмиттером из JSON, а правки пользователя разбираются
  своим парсером и отдаются kubectl уже JSON-ом — серверный YAML приложению читать не нужно.
- `KubeLens --cluster` при запуске сразу открывает окно ресурсов текущего контекста (для отладки).
